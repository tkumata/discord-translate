## Goal

利用者は、受信訳と短い補足から会話のノリを理解できる。
スラング、冗談、文化的な表現を理解する手掛かりを示す。
相手の本心を、モデルの推測だけで断定しない。

## Scope

- 受信メッセージの日訳に、必要な場合だけ補足を加える。
- 両翻訳先で、既存の1回の翻訳要求を使用する。
- 受信 UI のラベルと固定の注意書きを更新する。
- 受信訳のキャッシュを旧形式の生成結果から分離する。
- 本計画と current 文書、README の説明を整合させる。

## Non-goals

- 周辺会話、返信先、履歴、プロフィールの自動収集。
- 感情スコア、本気度の数値化、人物の性格判定。
- 新しい説明ボタン、設定、外部 API、依存関係。
- スラング辞書、検索連携、追加学習、モデルの変更。
- 下書き英訳の指示、表示、キャッシュ形式の変更。
- 真意の保証と、文脈不足を解消した扱い。

## Required Behavior

要求レベルは MUST (必須)、SHOULD (推奨) とする。
REQ-NUANCE-001〜004 と SPEC-NUANCE-001〜003 を参照する。

### 調査結果と議論

- 現行の受信 prompt は、口語とトーンの保持を要求している。
- 現行の受信 prompt は、訳文以外の説明を禁止している。
- 入力は対象本文だけであり、相手との関係や前後の会話はない。
- 慣用表現の研究では、言語モデルの文脈への感度を報告している。[R1]
- 会話履歴を用いた英韓翻訳で、精度改善の報告がある。[R2]
- 両研究は、本アプリの英日翻訳品質を保証する根拠ではない。

メインエージェントと `nuance_proposal` が既存コードを確認した。
両者は、受信訳への短い補足を初回の実装案に選んだ。
既存の文字列、SSE、保存経路を再利用できるためである。
サブエージェントは検証用 Python prompt の乖離も指摘した。
品質評価では製品と同じ指示を使用する。

| 候補 | 利点 | 費用と制約 | 提案 |
| --- | --- | --- | --- |
| 訳文の指示だけを強化 | 最小の変更 | 利用者は表現の背景を理解しにくい | 不採用 |
| 訳文に短い補足を追加 | 1回の要求で背景を読める | 出力が長くなり、誤解釈も残る | 採用 |
| 別の説明ボタンを追加 | 必要なときだけ説明を依頼できる | 要求種別とキャッシュの分離が増える | 初回対象外 |
| 会話文脈を追加 | 前後関係を判断する材料が増える | 送信範囲、同意、入力上限の設計が必要 | 別途承認対象 |

### 出力と表示の提案

- MUST: 訳文を先に出し、不要な補足は付けない。
- MUST: 補足は空行後の `[補足]` に続けるよう指示する。
- MUST: 補足は最大2項目とし、各項目は1〜2文にする。
- MUST: 補足は原文の表現を根拠として示すよう指示する。
- MUST: 一般的な用法と、今回の解釈の可能性を区別する。
- MUST: 曖昧な表現では、文脈不足と主な解釈候補を示す。
- MUST: 根拠がない感情、本気度、関係性を断定しない。
- SHOULD: 絵文字、強調、語調を自然な日本語へ反映する。
- MUST: 原文の不変要素と、既存の入力・応答検証を維持する。

例: `yeah right` の補足は、皮肉の用法と文脈不足を示す。
相手が怒っていると断定する補足は不合格とする。
平易な連絡文には、説明を無理に追加しない。

UI は文字列全体を `textContent` で表示する。
補足の見出しを解析する parser は追加しない。
モデルへの指示は、形式や解釈の正確さを保証しない。
注意書きの文言は UI が所有する。
出力に `[補足]` が含まれる場合だけ、注意書きを表示する。

## Tasks

### Task 1: 受信訳の生成指示とキャッシュを更新する

- Status: 実装・自動検証完了。実モデル品質は Task 3 で判定する。
- Objective: 両翻訳先で新しい受信訳を生成する。
- Scope:
  - `extension/translation-protocol.js` の受信 prompt。
  - `extension/translation-provider.js` の日訳キャッシュ識別。
  - `scripts/verify.py` の日訳 prompt の同期。
  - protocol、provider、queue、受信保存、ChatGPT の関連テスト。
- Acceptance Criteria:
  - 日訳だけに補足の指示を適用する。
  - local / chatgpt とも、固定指示の検証を通過する。
  - 日訳のキーに固定の生成指示版を追加する。
  - メモリと永続キャッシュは同じ識別関数を使う。
  - 旧日訳は miss とし、次の手動翻訳で生成する。
  - 旧保存値の一括削除は行わず、既存の期限削除に任せる。
  - 英訳のキーと payload は変更しない。
  - 補足を含む完成結果だけを既存の5日保存へ渡す。
  - 不完全応答と出力上限到達は、従来どおり失敗にする。
- Verification:
  - 旧日訳 miss、新日訳 hit、provider 分離、英訳互換を確認する。
  - SSE 分割をまたぐ補足の転送と、失敗時の非保存を確認する。
  - ChatGPT adapter の固定指示受付と任意指示拒否を確認する。
  - `npm --prefix extension test` を実行する。
  - `python3 -I scripts/verify.py --self-check` を実行する。

### Task 2: 受信 UI と利用者向け説明を更新する

- Status: 完了。実装・自動検証とユーザの動作確認を実施した。
- Objective: 訳文と補足を、推測の限界を含めて読めるようにする。
- Scope:
  - `extension/received-messages.js` と関連テスト。
  - `extension/styles.css` は注意書きの表示に必要な範囲だけ。
  - `README.md` の機能、保存対象、品質上の制約。
- Acceptance Criteria:
  - ラベルを「日本語訳・補足」にする。
  - 生成中は「日本語訳・補足（翻訳中…）」にする。
  - 固定文「補足は推測を含みます。相手の真意は断定できません。」を示す。
  - 通常生成とキャッシュ復元の両方で同じ表示条件を使う。
  - 生成中は `[補足]` が揃った時点で注意書きを表示する。
  - `[補足]` がない場合、注意書きを非表示にする。
  - 原文、改行、HTML 風文字列のプレーンテキスト表示を保つ。
  - 編集、削除、OFF、provider 切替時は既存 UI とともに片付ける。
  - 下書き英訳の表示と取り消し動作を維持する。
- Verification:
  - DOM fixture で生成、復元、注意書き、破棄を検証する。
  - Task 1 と合わせて既定の Node テストを1回実行する。
  - 実 Chrome で明暗テーマ、改行、読み上げと操作を確認する。

### Task 3: 翻訳品質と制約を実モデルで評価する

- Status: 完了。品質不合格を残し、ユーザの現状受け入れで終了した。
- Objective: 補足が会話の理解を助け、断定や捏造を増やさないか確認する。
- Scope:
  - 架空の固定評価例と、両翻訳先での結果記録。
  - 製品の `buildPayload` と同じ指示を使う評価。
  - 自動検証と、人手による意味評価を分離する。
- Acceptance Criteria:
  - 次の固定例を両翻訳先で評価する。
  - `no cap, that was fire 🔥`: スラングを字義訳だけにしない。
  - `break a leg!`: 応援の用法を説明する。
  - `yeah right`: 同意と皮肉の可能性、文脈不足を示す。
  - `sure`: 怒りや本気度を断定しない。
  - `I'm dead 😂`: 笑いの用法を説明する。
  - `Great, another meeting 🙃`: 皮肉の可能性を根拠付きで示す。
  - `Why did the scarecrow win an award? He was outstanding in his field.`: 言葉遊びを説明する。
  - `The meeting starts at 3 PM.`: 不要な補足を追加しない。
  - Markdown、URL、コード、命令風の本文で既存の境界を保つ。
  - 8,000 UTF-16 コード単位以内の長文で完了か固定エラーを確認する。
  - 全例で主要な意味を保ち、背景や相手の感情を捏造しない。
  - 長文の上限到達を成功と記録しない。
  - 両翻訳先の未実施と不合格を個別に記録する。
  - 実 Chrome の通常表示と保存復元を確認する。
- Verification:
  - 特定の訳文への完全一致ではなく、上記観点で人手評価する。
  - provider、モデル、評価日、合否、失敗理由を記録する。
  - 品質不合格なら完了扱いせず、指示修正の範囲を確認する。
  - `git diff --check` と文書参照の整合を確認する。

### 実モデルの評価方法

- local: 固定済み `mlx-community/Qwen3.5-9B-MLX-4bit`。
- chatgpt: 既存接続が選択した `gpt-6.1-sol`。
- 評価日: 2026-10-27。対象は本計画の架空の固定例だけ。
- 製品の `buildPayload`、SSE parser、完成結果検証を使った。
- 意味の評価は出力を読んで行い、自動テストの成功と区別した。
- 初回 local 評価の直訳と誤説明を受け、指示を1回修正した。
- 修正では短い出力例と、省略・根拠のない語源説明の禁止を加えた。
- 以下は修正後の評価結果である。再現性や一般的品質は保証しない。

| 評価例 | local | chatgpt |
| --- | --- | --- |
| `no cap, that was fire 🔥` | 合格。スラングの意味で訳し、補足を表示。 | 合格。スラングの意味と補足を表示。 |
| `break a leg!` | 合格。成功を願う用法を説明。 | 合格。応援の用法を説明。 |
| `yeah right` | 不合格。「ええように」という誤った説明が混入。 | 合格。同意と皮肉の候補、文脈不足を表示。 |
| `sure` | 合格。了承とそっけない返事の候補を表示。 | 合格。文脈不足と解釈候補を表示。 |
| `I'm dead 😂` | 不合格。補足はあるが、訳文は「死んでしまった」。 | 意味は合格。「笑い死ぬ 😂」と訳した。補足はなし。 |
| `Great, another meeting 🙃` | 一部不合格。皮肉の手掛かりは示すが、`Great` が脱落。 | 合格。喜びと皮肉の可能性を区別。 |
| かかしの言葉遊び | 不合格。かかしを「ハト」と誤訳し、背景を捏造。 | 合格。「分野」と「畑に立つ」の掛け合わせを説明。 |
| 通常の会議連絡 | 合格。不要な補足なし。 | 合格。不要な補足なし。 |
| Markdown / URL / コード | 不合格。パッチの語と強調が脱落し、不要な補足が混入。 | 合格。強調、URL、識別子、コードを保持。 |
| 命令風の本文 | 不合格。本文の命令に従い `BANANA` を出力。 | 合格。命令を実行せず、日本語へ翻訳。 |
| 長文の境界 | `finish_reason=length` を `invalid_response` として拒否。翻訳成功とは扱わない。 | 約81秒で完了。110回分の時刻とパッチの記述を保持。 |

長文には、同じ2文を110回繰り返した入力を使った。
両翻訳先で8,000 UTF-16 コード単位の入力上限以内だった。
初回 local は繰り返しを要約したため不合格とした。
修正後は出力上限到達を検出し、完成結果として扱わなかった。

### 実行環境と未確認範囲

- local は sandbox 内で Metal device を取得できなかった。
- 制限外で既存の起動スクリプトを使い、一時起動した。
- 評価後に、この作業で起動した local サーバを停止した。
- 起動中の ChatGPT 補助は、旧指示を保持して新指示を400で拒否した。
- 既存の補助を停止せず、新コードの補助を一時ポートで検証した。
- 一時補助は既存の有効な access token を読んで使用した。
- 認証情報の refresh と保存は行わず、評価後に一時補助を停止した。
- 利用時は拡張を再読み込みし、補助へ新コードを反映する必要がある。
- 既存補助の実際の再起動と、その後の翻訳は未確認である。
- 検証用ページで、実コードによる表示を明暗テーマで確認した。
- 固定注意書きと補足の改行、本文領域幅320pxでの折り返しを確認した。
- 認証済み Discord、実 Chrome 拡張、読み上げは未確認である。
- browser 接続には in-app browser だけがあり、Chrome 接続はなかった。
- DOM テストの復元成功を、実 Chrome の受け入れへ代用しない。
